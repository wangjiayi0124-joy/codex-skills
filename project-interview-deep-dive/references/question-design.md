# 问题与深挖规则

## 从真实面试路径设计问题

先找“面试官为什么会继续问”，再确定问题。常见起点包括：项目总述、本人做了什么、为何做这个功能、MVP 如何收敛、最大挑战、效果如何、复盘如何改进。

## 先搭问题树，再填功能案例

面试官通常不了解项目，不会一开始就问某个字段、页面或排序规则。先用粗问题建立一级路径，再逐层下钻。常见顺序是：

1. **讲讲整个项目** → 为什么做、对谁有价值、当前阶段。
2. **你具体做了什么** → 本人边界、独立工作、外部依赖。
3. **设计上最复杂的部分是什么** → 角色/权限、关键链路或信息架构。
4. **最大的挑战是什么，如何推进** → 研发或协同中的具体分歧、判断和落地案例。
5. **如何收敛范围或做关键取舍** → 初始方案、放弃内容、分期和风险控制。
6. **上线后如何衡量、如何复盘** → 当前阶段、数据口径、护栏和下一步。

按项目删减、合并或调整，不要把它当固定题库。若“为什么做”和价值只能在项目总述下讲清，就作为“讲讲整个项目”的追问，而不是拆成重复一级题。

将每个案例放入最能解释它出现原因的上层问题。逐项检查：

1. 一个不熟悉项目的面试官，是否会在未了解背景前自然问到它？若不会，不设为一级题。
2. 它是一个独立业务判断，还是现有问题下的具体证据、分歧或决策？后者放入相应追问。
3. 它是否承载项目最核心的业务判断、真实冲突或可验证成果？只有满足这一条件，才考虑升为一级题。

不要把同一案例同时写成一级路径和某条路径的追问；需要从不同视角引用时，保留一条完整回答链，其他位置只简短指向该案例。

将项目中的真实矛盾转为独立问题，而不是把它们塞进同一题。示例逻辑：

- 有方案前后变化：问“为什么从初始方案改成最终方案？”
- 有角色利益冲突：问“为什么这样做不会伤害合作方/另一角色？”
- 有不确定效果：问“你如何灰度/验证，而不是直接全面推开？”
- 有跨部门依赖：问“最大挑战是什么？你如何明确负责人、边界和交付？”
- 有 AI 能力：问“Agent 的边界、触发、人工兜底和效果怎么设计？”

## 使用四类深挖视角，但不要机械套用

以下四类是发现问题的视角，不是每道题都要遵循的答题框架：

1. **判断逻辑**：为什么这样选？是否考虑公司战略、业务指标、用户需求、成本、周期、生态约束或风险？
2. **行动过程**：不是只列措施；说明初始方案、替代方案、调研发现、核心链路优化和最后的取舍。
3. **可迁移能力**：协助工作也可拆出对齐需求、整理复杂信息、推进反馈、发现流程漏洞、把模糊问题变成行动。
4. **真实拉扯**：资源不足、周期紧、跨部门难推、方案上线后数据一般、合作方冲突等。说清限制与处理，比只报好结果更可信。

## 选择回答结构

- **按维度**：只有不同角色或利益点真的不同，例如客户、合作方、平台、实现成本。
- **按时间**：适合协同推进、问题解决和方案演变。
- **按因果**：适合决策、MVP 取舍和指标设计。

不要把一句本可合并的因果关系拆成两条平级内容；也不要为了整齐把“挑战”与“价值”放在同一层。

## 思考与升华的证据边界

- 从项目中的选择、数据、反馈、限制和复盘提炼，不从空泛概念出发。
- 区分：**已验证结论**、**当前判断**、**待验证假设**。
- 方法论必须能够回到本项目的具体证据，且表达为可迁移的做法，不夸大为普适规律。
- 不要只写“底层价值、方案取舍、复盘”等目录名。每项改写成面试中可被问到的问题，并给出答案；每个答案至少包含一个项目事实和一个适用边界。

## 完整交付的最低结构

除非用户明确只要简版，最终档案应包含：

1. 项目摘要、事实边界与多角色价值地图（若适用）；
2. STAR；
3. 4–7 条一级面试问题树，每条有考察点、首轮回答、追问和回答抓手；
4. 4–6 条项目思考问答；
5. 待补充项与不可夸大的结果。

## AI/Agent 的补充提问

根据材料选择，而非全部强行使用：

- 为什么引入 Agent，而不是只优化人工流程？
- Agent 应该优先承接、辅助人工还是兜底？为什么？
- 什么情况下触发？根据什么信息判断？
- 错误回复、误推荐、打扰用户或伤害合作方关系如何防范？
- 如何逐步灰度和衡量效果？灰度不等于 A/B Test；按实际方法表述。
